From a rough idea to ordered, executable development phases — files a coding agent can build from.

Spec4 turns an idea into a set of structured, ordered development phases — plus an optional UI mock and a deployment plan — that you hand to whichever coding agent you use. Everything it produces is a file in a .spec4/ folder inside your project. It runs on your machine, talks only to the model provider you choose, and keeps your API key in your browser.

It is not a coding agent. It doesn't write your application; it writes the plan your coding agent builds from — with the failure modes, acceptance criteria, and deployment configuration a production system needs, not just the happy path. And the plan is not written once: each pass over the project is a new round, planned against the code as it actually exists.

  • Runs locally. A local process; the only network calls are to the model provider you chose and, if you enable it, the search provider.
  • Your code stays in the repo. CodeScanner reads it locally and sends the model a bounded summary — manifests, entry points, samples — not the tree.
  • Your keys, in your browser. Anthropic, AWS Bedrock, Cohere, Google Gemini, Mistral, Nebius, OpenAI, or OpenRouter. Held in localStorage, opt-in; never written to disk; never sent anywhere but the provider they belong to.
  • Any model, any step. A default for the pipeline; a different provider, model, and reasoning effort for any agent, chosen when it starts or on a retry after a provider error.
  • Any coding agent. Plain Markdown and JSON with no agent-specific format; Deployer writes the setup instructions for the agent you name. The folder is documented. Artifacts
  • Apache 2.0. Free. You pay your provider, and every round records what it cost.

.spec4/
└── v1/                        # one directory per planning round

    ├── vision.json            # Brainstormer — purpose, audiences, MVP features
    ├── feature_specs.json     # Brainstormer — a behavioral spec per MVP feature
    ├── ai_catalog.json        # Agentifier — its recommendation and your decision, per feature
    ├── ai_features.json       # Agentifier — where AI belongs, at what tier, built how
    ├── design/
    │   ├── mock.html          # Designer — a self-contained mock of the starting screen
    │   └── manifest.json      # Designer — the design decisions the mock embodies
    ├── stack.json             # StackAdvisor — the technology stack, with canonical doc links
    ├── phases/                # Phaser — ordered phase files, one per implementation step
    │   ├── phase1.md
    │   ├── phase2.md
    │   └── ...
    ├── deployment-plan.md     # Deployer — infrastructure, CI/CD, config files, Terraform
    ├── usage.json             # what each agent cost this round, per call
    └── IMPLEMENTED            # the coding agent's marker that the round is built

Three kinds of file. The phase files are prompts for the coding agent. The JSON and the mock are reference for the agent: the decisions it grounds against. deployment-plan.md and usage.json are a record for you. Artifacts

The phase files are the point. Each one is written for a coding agent, not for you. This is from Spec4's own repository — .spec4/v0/phases/phase1.md, the first phase of the round that reworked this app's UI, and the thing a coding agent is handed:

# Phase 1 of 7: Integration Thread — Baseline Validation of the Existing Spec4 App

Prove the existing Dash application builds, serves at localhost:8050, and passes
its full quality gate (pytest, ruff, mypy) unchanged, and read the existing
callback co-presence contract so the coming shell rework is done against a
known-green baseline rather than a guessed one. No feature work, no layout
changes, no new files.

## Tech Stack

**Dependencies:** uv, dash, dash-mantine-components, pytest, pytest-cov, ruff, mypy, …

**Configurations:** No required env vars. Optional: DASH_DEBUG (enables Dash
hot-reload), LITELLM_LOG (must be set before litellm is first imported). App
serves HTTP on localhost:8050 only.

## Instructions

1. Run `uv build` and confirm it completes without error using the existing
   uv_build backend and pyproject.toml; do not modify pyproject.toml.
2. Run `uv run pytest` and record the number of passing tests. This count is
   the baseline that every later phase must match or exceed.
3. Run `uv run ruff check src tests` and `uv run mypy src`; both must exit 0.
   Do not add `# noqa` or `# type: ignore` to make them pass.
4. Start the app with `uv run spec4` and confirm that GET http://localhost:8050/
   returns 200 and renders the directory picker for an empty directory.
5. Read src/spec4/callbacks/__init__.py and every module it imports. List each
   callback whose Output targets a component id that is not present in every
   layout the app can render (the co-presence contract Dash enforces at
   runtime, not at import time).
6. Write that list, and nothing else, to .spec4/v0/notes/callbacks.md, one
   line per callback: `<module>:<function> → <component id>`.

## Risk Assessment

- **Hallucinated component ids.** Dash raises only when a callback fires
  against an id absent from the current layout, so a wrong id survives the
  test suite. Mitigation: enumerate ids from the layout modules by reading
  them, not from memory of how Dash apps are usually structured.
- **The test suite reaches the network.** Several tests construct a litellm
  client. Mitigation: confirm `SPEC4_OFFLINE=1` is respected by conftest.py
  before running; if any test opens a socket, stop and report rather than
  patching the test.
- **Scope creep.** The shell rework is Phase 2. Mitigation: this phase adds
  no files other than the notes file and modifies none.

## Verification

`uv build && uv run pytest && uv run ruff check src tests && uv run mypy src`
all exit 0; `curl -s -o /dev/null -w '%{http_code}' localhost:8050/` prints
200; and .spec4/v0/notes/callbacks.md exists with at least one line.

## References

- Dash callbacks and layout validation: https://dash.plotly.com/basic-callbacks
- uv build backend: https://docs.astral.sh/uv/concepts/build-backend/

Seven agents produce those files, in order. Each reads what the ones before it wrote.

Agent Reads Writes Runs
CodeScanner your repository, locally; the model gets a bounded summary code_review.json when there is code
Brainstormer code_review.json, your answers vision.json, feature_specs.json every round
Agentifier vision.json, feature_specs.json ai_catalog.json, ai_features.json optional
Designer vision.json, ai_features.json, your screenshots design/mock.html, design/manifest.json optional
StackAdvisor vision.json, ai_features.json, code_review.json, design/manifest.json stack.json every round
Phaser everything above phases/phase1.md … phaseN.md every round
Deployer phases/, stack.json, feature_specs.json, design/mock.html deployment-plan.md, optionally README.md when deployment changes

Brainstormer, StackAdvisor, and Phaser are the spine. CodeScanner is required whenever there is code to read. The other three are optional, and skipping one is a decision the later agents can see: a round without Designer produces phases that leave the look to the coding agent; a round without Agentifier produces no AI features at all.

How a round works

A round is one pass through the pipeline. Its output is a folder — .spec4/v0/ for the first round, v1/ for the next, and so on. The project page lists the seven agents in order with one button each, and the button's label is computed from the files on disk every time the page renders: Start when an agent's inputs exist and its output doesn't, Modify when its output is at least as new as everything it depends on, Needs Update when something upstream changed after it ran. Nothing is cached, so editing a file by hand has the same effect as re-running the agent that wrote it.

The last phase's final instruction is touch .spec4/v{N}/IMPLEMENTED. When your coding agent has built the phases, that marker is what tells Spec4 the round is done and the next one may begin. The next round starts with CodeScanner reading what was actually built — including anything you or the agent changed that the plan didn't say. That is the difference between planning against the code and planning against the last plan. Rounds

In a revision round Brainstormer does not re-ask the nine questions. The product's identity is settled; it states what's built and asks what this round is for — what to add, change, or remove — and works those one at a time. The result is written to vision.json as a full vision, never a diff, with one more entry in revision_history, and every agent downstream reads that last entry as the delta it scopes to.

What it is not

Spec4 does not write code, run your tests, open pull requests, or talk to your coding agent. It has no plugin for Claude Code or Cursor and needs none: the output is Markdown and JSON on disk, and the coding agent reads it the way it reads any other file in the repository. Deployer writes the first section of deployment-plan.md for the agent you name — how to start it in the project directory, where the Spec4 files live, the exact syntax to reference a phase file — and that is the whole integration.

It is also not a chat window over your codebase. Each agent asks one question at a time and only what it needs, and the answer is written to a file with a schema. If a schema check fails, the agent is told what failed and tries again; you see the retry, and the file isn't written until it passes. The conversation is the means; the file is the result.

It is not free of judgment calls. Phaser may not add a component, library, or service that isn't in the approved stack, not even when the choice seems obvious. It stops and asks, and on your yes records a stack_addition in stack.json. The plan you hand over is one you approved line by line, which is slower than a plan you didn't, and the reason the coding agent can trust it.

What it costs

Spec4 is Apache 2.0 and there is nothing to buy. You pay your model provider directly. Every call is priced from litellm's community cost map and written to usage.json, and the project page shows the round's estimate above the tree. The estimate is an estimate: the cost map can lag a provider's price sheet, and your provider's billing is authoritative.

For scale, Spec4's own three rounds on its own repository, on a mid-tier model, ran between $3 and $5 each. The two largest line items are StackAdvisor, which reads every canonical documentation page it cites, and Phaser, which reads everything above it and emits every phase at once. A greenfield round with a short vision and five phases is a fraction of that. A round that skips Designer and Deployer, as most revision rounds do, is smaller again.

Reasoning effort is a per-agent setting. A default for the pipeline, and a different provider, model, and effort for any agent, chosen when it starts or on a retry after a provider error. The usual arrangement is a cheap model for CodeScanner, whose job is transcription, and a stronger one for Phaser, whose job is the plan. Settings

Providers and keys

Eight providers: Anthropic, AWS Bedrock, Cohere, Google Gemini, Mistral, Nebius, OpenAI, and OpenRouter. All go through litellm, so a model is a string and switching is a settings change. Keys are held in your browser's localStorage, opt-in — the alternative is to paste the key each session — and the local process reads them from the request, not from disk. Nothing under .spec4/ contains a key, so the folder can be committed.

Web search is optional and separate. With a Tavily or Exa key, Brainstormer looks up the canonical documentation for any standard or SDK you name, StackAdvisor verifies each component it recommends against its current docs, and Deployer checks pricing and free tiers before it names a service. Without a key, every agent still runs; it just can't look anything up, and the phase files say so in their References.

Where the plan can be wrong

Three places, and Spec4 checks two of them deterministically. First, a phase set can be incomplete: a feature no phase declares, a number missing from 1 to k, infrastructure stood up after the first phase that needs it. These are validated after the model emits the set, and a failure goes back to the model with the fault named. Second, on a greenfield set, a phase can read a table before another creates it or call an endpoint before one defines it. A second call extracts a data-flow graph from the phases and the checks are run over it; findings are shown next to the ready phases and never block.

The third is the one it can't check: the plan can be a faithful plan for the wrong product. That is what the conversations are for, and why every agent shows you its work before it writes the file. Read the phases before you hand them over. They are written for a coding agent, but they read the same to a person.

Spec4 docs

Spec4 is a local tool that turns a rough idea, or a change to an existing codebase, into a set of ordered development phases written for a coding agent. Seven planning agents run in order. Each reads what the ones before it wrote, and everything they write is a file under .spec4/ in your project. Spec4 doesn't write code; your coding agent does, one phase at a time.

Install

Requires Python 3.12+ and uv, plus an API key for at least one supported provider.

uv tool install spec4 --refresh
spec4

From source:

git clone https://github.com/robertcrowe/spec4
cd spec4
make spec4

Either way the app is at localhost:8050. To upgrade: uv tool upgrade spec4 (PyPI) or git pull && make install (source). Upgrades never touch your artifacts; everything lives in .spec4/ inside your project.

First run

  1. Pick a project directory. An empty directory is a new project. A directory with files in it gets one question — Is there an existing project here? — because a uv init skeleton and a codebase you're modifying look the same to a file listing. Existing project starts with CodeScanner; New project starts with Brainstormer. You're asked again next session; the answer isn't written to disk.
  2. Connect a provider. Choose one of eight — Anthropic, AWS Bedrock, Cohere, Google Gemini, Mistral, Nebius, OpenAI, or OpenRouter — enter its key, and pick a default model and reasoning effort. The key is held in your browser's localStorage, opt-in, and is never written to disk or sent anywhere but the provider it belongs to. Optionally add a Tavily or Exa key so the agents can ground their recommendations with live search. Settings
  3. Start the first agent. The project page lists the seven agents in order with one button each. Press Start on the first one that offers it.

The buttons

Each agent's row on the project page carries one button. Its label is computed from the files on disk every time the page renders; nothing is cached.

Button Meaning
StartThe agent's inputs exist and it hasn't produced its output yet.
ContinueSame as Start, but this session already has an unfinished conversation with the agent.
ModifyThe agent's output exists and is at least as new as every input it depends on.
Needs UpdateThe output exists, but an upstream artifact has changed since it was written.
Not ReadyA required input is missing, or the inputs are out of order — an upstream artifact is newer than one downstream of it.
RequiredThe previous round is implemented and the next hasn't started. Only CodeScanner shows this, because every round after the first begins with a re-scan.

A hand edit has the same effect as a re-run: save vision.json and every agent that reads it turns to Needs Update. The timestamps on disk are the whole state machine.

Pages

  • CodeScanner — reads an existing directory and writes code_review.json, every fact with its source.
  • Brainstormer — develops the vision one question at a time; writes vision.json and feature_specs.json.
  • Agentifier — finds where AI belongs and recommends a tier from a nine-rung ladder; writes ai_catalog.json and ai_features.json.
  • Designer — a short wizard that draws the starting screen as one HTML file; writes design/mock.html and design/manifest.json.
  • StackAdvisor — recommends the stack component by component, each with a canonical doc link; writes stack.json.
  • Phaser — turns everything above into ordered phase files, steel thread first; writes phases/.
  • Deployer — asks which coding agent you use and writes deployment-plan.md, configuration files included.
  • Artifacts — every file in .spec4/: who writes it, who reads it, what it looks like.
  • Rounds — greenfield, brownfield, and revision rounds, and what IMPLEMENTED means.
  • Settings — providers, keys, per-agent models and reasoning effort, web search.

The recommendation and the decision

Agentifier writes its recommendation and the developer's decision to the same file. From .spec4/v0/ai_catalog.json:

{
  "name": "rag_example_app",
  "tier_recommendation": "single_call",
  "tier_decision": "rag",
  "tier_decision_rationale": "The whole point of this example is to illustrate the use of RAG, so the retrieval pipeline is the feature, not an escalation past it.",
  "over_engineering_signs_acknowledged": [
    "Corpus is small enough to fit in a single prompt"
  ],
  "decided_by": "developer",
  "decided_at": "2026-05-31T14:02:11Z"
}

The Tier Analyst recommended single_call because the corpus fits in one prompt, which is the rule it is given. The developer overrode it and wrote down why. Both survive in the file, and the phase that builds the feature quotes the rationale.
